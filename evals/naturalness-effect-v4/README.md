# 이상한 한국어 표현을 실제로 고치는가

다음 문장들은 문법적으로 완전히 틀렸다고 하기는 어렵습니다.

> 두 variant의 parity를 확보한다.
>
> 상태를 화면으로 꺼낼 구멍을 연다.
>
> 호출 경유, 변경 불요.
>
> 처음부터 켜두는 편이 쌉니다.

그러나 독자는 `variant`와 `parity`가 무엇인지 앞 문맥에서 다시 찾거나, `구멍을 연다`를 API 응답 속성 추가라는 동작으로 바꾸거나, 생략된 주체와 서술어를 채워야 합니다. 이 저장소의 목적은 문장을 화려하게 다듬는 것이 아니라 **이처럼 뜻을 한 번 더 복원하게 만드는 표현을 찾아 실제 대상과 동작이 드러나는 한국어로 고치는 것**입니다.

앞선 [문맥 효과 실험](../context-effect-v3/README.md)은 모델이 뜻을 확정할 수 있는지, 확정할 수 없을 때 수정을 멈추는지를 주로 측정했습니다. 이번 실험은 뜻을 확정할 수 있는 문맥만 주고 다음 질문을 직접 측정합니다.

1. 모델이 이상한 표현을 고쳐야 할 문장으로 알아보는가?
2. 수정문에서 문제 표현을 실제로 버리는가?
3. 문제 표현을 버리면서도 문맥의 핵심 뜻을 남기는가?
4. 이미 명확한 문장은 불필요하게 고치지 않는가?

## 평가 설계

회사 문서나 사내 발췌문은 사용하지 않았습니다. [`tasks.json`](tasks.json)에 공개용 합성 사례 12개를 만들었습니다.

- 이상 표현 9개: 낯선 혼합어 2개, 임의의 비유 2개, 명사 압축 1개, 설명을 대신하는 평가 2개, 구어적 비유 1개, 임의 음역어 1개
- 대조 문장 3개: 팀 용어집에 정의된 영어 용어, 코드 식별자, 주체와 동작이 이미 분명한 문장

모든 이상 표현에는 뜻을 하나로 확정할 수 있는 긴 문맥을 붙였습니다. 따라서 모델이 `의미 확인 필요`로 물러나는 능력보다, 주어진 사실을 사용해 표현을 고치는 능력을 봅니다. 대조 문장은 영어가 보인다는 이유만으로 `Kafka lag`, `messageUuid`, `notification.tag`까지 고치는 과잉 교정을 찾습니다.

2026년 9월 3일 Claude Code 2.0.73과 Codex CLI 0.151.0-alpha.7.2, Ollama Cloud Responses API에서 다음 10개 모델에 같은 12개 사례를 한 번씩 묶어 보냈습니다.

| 경로 | 모델 지정값 |
|---|---|
| Claude Code | `claude-fable-5`, `sonnet`, `claude-haiku-4-5` |
| Codex CLI | `gpt-5.6-sol`, `gpt-5.4-mini`, `gpt-5.3-codex-spark` |
| Ollama Cloud Responses API | `kimi-k3`, `glm-5.2`, `qwen3.5:397b`, `gpt-oss:120b` |

`sonnet`은 Claude Code에 전달한 별칭을 그대로 기록한 값입니다. 제공자가 별칭이 가리키는 배포 모델을 바꿀 수 있으므로 고정된 모델 버전으로 취급하지 않습니다.

각 모델에는 두 조건을 적용했습니다.

- `none`: 자연스럽고 명확한 한국어 기술 문장인지 검토하라는 과제와 출력 형식만 제공
- `baseline`: 같은 과제에 현재 배포 스킬의 `SKILL.md`와 참고 문서 3개를 시스템 또는 개발자 지침으로 추가

네이티브 스킬 검색 기능의 유무가 아니라 **같은 지침 내용이 결과에 미치는 영향**을 비교합니다. 총 20회 호출에서 240개 사례 판정을 얻었고, 모든 호출과 JSON 출력이 완료됐습니다.

## 무엇을 점수로 삼았는가

문장이 수려한지는 점수로 삼지 않았습니다. 다음 항목을 각각 계산했습니다.

- **이상 표현 제거율:** 미리 정한 문제 표현이 수정문에서 사라졌는가?
- **핵심 의미 포함률:** 수정문에 문맥의 대상, 동작, 조건이 남았는가?
- **수정 성공률:** 기대 판정, 실제 수정, 이상 표현 제거, 핵심 의미 포함, 근거 없는 내용 미추가를 모두 만족했는가?
- **정상 문장 보존율:** 대조 문장을 `통과`시키고 수정문을 만들지 않았는가?

핵심 의미 포함률은 두 방식으로 공개합니다. `exact`는 처음 적은 필수 문자열을 그대로 찾습니다. `patterns`는 `재계산/다시 계산`, `입력값/입력한 값`처럼 같은 뜻의 명백한 형태 차이를 허용합니다. 형태 차이를 허용하는 규칙은 원출력을 본 뒤 추가했으므로, 결과를 하나만 고르지 않고 두 점수를 함께 남겼습니다. 이상 표현 제거율과 정상 문장 보존율은 이 보정의 영향을 받지 않습니다.

## 결과

### 목표에 가장 가까운 지표는 개선됐다

| 지표 | 지침 없음 | 현재 스킬 | 차이 |
|---|---:|---:|---:|
| 이상 표현 제거율 | 83.3% | 95.6% | **+12.3%p** |
| 핵심 의미 포함률 `exact` | 17.8% | 38.9% | +21.1%p |
| 수정 성공률 `exact` | 14.4% | 37.8% | **+23.4%p** |
| 핵심 의미 포함률 `patterns` | 36.7% | 51.1% | +14.4%p |
| 수정 성공률 `patterns` | 31.1% | 48.9% | **+17.8%p** |
| 정상 문장 보존율 | 100% | 100% | 0%p |

현재 스킬은 이 표본에서 문제 표현을 더 자주 버렸고, 수정 과정에서 핵심 뜻을 남기는 비율도 높였습니다. 영어 용어와 코드 식별자를 포함한 대조 문장 30건은 두 조건 모두 전부 통과시켰습니다. 따라서 이번 결과에서 나타난 개선은 모든 영어를 한국어로 바꾼 결과가 아닙니다.

### 좋은 수정은 비유를 다른 비유로 바꾸지 않았다

`gpt-5.6-sol`의 스킬 적용 결과는 다음처럼 실제 구성 요소와 동작을 드러냈습니다.

| 원문 | 수정문 |
|---|---|
| 상태를 화면으로 꺼낼 구멍을 연다. | 서버가 계산한 `status` 값을 화면이 읽을 수 있도록 API 응답 객체에 추가한다. |
| 이벤트를 정산 파이프에 태운다. | 주문 서비스가 `payment_completed` 이벤트를 Kafka의 `settlement-events` 토픽에 발행한다. |
| 이 방식은 회계 오염을 막는다. | 기존 분개를 변경하지 않고 사유와 승인자가 기록된 조정 전표를 추가하므로, 원래 분개 이력과 수정 근거를 모두 보존할 수 있다. |
| 처음부터 켜두는 편이 쌉니다. | 추가 메모리 비용보다 응답 시간 개선이 더 중요하므로 모든 운영 서버에서 기동 시 사전 적재를 활성화한다. |

Fable 5도 스킬 조건에서 9개 이상 표현의 수정 성공 조건을 모두 만족했습니다. 무지침 조건에서도 수정문 자체는 대체로 충실했지만, 뜻이 충분히 주어졌는데도 일부 문장을 `의미 확인 필요`로 분류했습니다. 현재 스킬은 이 경우 판정과 수정 행동을 일치시키는 데 도움이 됐습니다.

### 표현만 지운다고 설명이 완성되지는 않았다

스킬 조건의 이상 표현 제거율은 95.6%였지만 형태 허용 수정 성공률은 48.9%였습니다. 문제 표현을 없앤 뒤 너무 짧게 줄여 핵심 대상을 다시 숨긴 사례가 있었기 때문입니다.

| 원문 | 실제 수정문 | 남은 문제 |
|---|---|---|
| 500대 fleet의 route recalculation fan-out을 제어한다. | 로봇 경로 재계산 작업의 동시 처리 묶음 수를 제한한다. | `qwen3.5:397b`는 500대, 25대씩, 최대 네 묶음이라는 범위를 생략했다. |
| 처음부터 켜두는 편이 쌉니다. | 기동 시 사전 적재를 활성화하는 것이 비용 대비 효과적이다. | 같은 모델은 무엇이 얼마나 개선되고 어떤 비용이 늘어나는지 다시 평가어로 압축했다. |
| 두 variant의 parity를 확보한다. | 두 화면의 표시 필드를 같게 맞춘다. | Haiku 4.5는 관리자용과 학생용이라는 두 대상을 생략했다. |

또한 Spark는 스킬 조건에서도 `variant`, `parity`, `fleet`, `route recalculation fan-out`을 다시 사용한 사례가 있었습니다. 현재 스킬은 평균적으로 도움이 됐지만, 모든 모델이 “원문 표현을 버리고 실제 대상과 동작을 쓴다”는 지시를 같은 강도로 따르지는 않았습니다.

### 효과는 표현 유형과 모델에 따라 달랐다

형태 차이를 허용한 수정 성공률은 구어적 비유에서 10%→60%, 동작을 대신하는 비유에서 30%→70%로 크게 올랐습니다. 반면 혼합어는 45%→40%, 음역어는 30%→20%로 한 번의 실행에서 낮아졌습니다. 혼합어와 음역어의 원문 토큰을 지우는 비율 자체는 각각 80%→90%, 60%→80%로 올랐지만, 수정문이 대상을 생략해 전체 성공 조건을 충족하지 못했습니다.

모델별 수정 성공률도 Fable 5는 67%→100%, `gpt-5.6-sol`은 56%→89%, GLM 5.2는 0%→67%로 올랐지만, Kimi K3는 100%→78%로 낮아졌습니다. 모델·조건별 한 번의 출력이므로 일반적인 모델 순위나 안정적인 하락으로 해석할 수 없습니다. 다만 긴 지침이 모든 모델에 같은 이득을 주지는 않는다는 앞선 관찰은 다시 확인됐습니다.

## 이번 실험에서 바뀐 결론

앞선 v3만 보면 스킬의 주된 가치가 “뜻을 모를 때 함부로 고치지 않는 안전장치”처럼 보였습니다. 그 설명은 의미 보존 측면에서는 유효하지만 이 프로젝트의 중심 질문은 아니었습니다.

목표를 이상한 한국어 표현의 실제 교정으로 다시 맞추자, 현재 스킬은 문제 표현 제거와 의미를 갖춘 수정에서 분명한 평균 개선을 보였습니다. 동시에 성공률이 절반에 못 미쳤다는 사실도 드러났습니다. 다음 개선은 규칙을 더 많이 나열하기보다 다음 한 가지를 강화해야 합니다.

> 수정문을 짧게 만드는 것보다, 원문의 이상 표현이 대신하던 대상·동작·조건·범위를 빠짐없이 문장에 되돌려 놓는다.

이 문장을 후보 지침으로 추가하려면 현재 결과를 기준선으로 고정하고 새 표본에서 다시 시험해야 합니다. 이번 실행의 원출력을 보고 곧바로 배포 스킬을 바꾸지는 않았습니다.

## Ollama Cloud 429 재확인

이전 실험에서는 Ollama Cloud 호출이 429로 끝났습니다. 이번에는 먼저 `kimi-k3` 한 조건을 동시성 1, 재시도 0으로 호출했고 61.183초 만에 정상 완료됐습니다. 이어서 네 모델의 두 조건을 동시성 1로 실행한 8회도 모두 완료됐습니다. 429는 재발하지 않았습니다.

Ollama Cloud 8회에서 입력 26,349토큰, 출력 30,822토큰, 합계 57,171토큰을 사용했습니다. 이 결과는 2026년 9월 3일 실행 시점의 가용성만 보여 주며, 과거 429의 원인이나 향후 제한을 확정하지 않습니다. API 키와 인증 정보는 결과에 저장하지 않았습니다.

## 한계

- 합성 사례 12개와 모델·조건별 1회 실행이므로 통계적 유의성이나 모델 일반 성능을 주장하지 않습니다.
- 문제 표현을 미리 정한 통제 실험이므로, 처음 보는 문서에서 이상 표현을 빠짐없이 발견하는 능력과는 다릅니다.
- 자동 점수는 알려진 문제 표현과 핵심 개념의 문자열·정규식 검사입니다. 한국어 자연스러움 전체를 자동 판정하지 않습니다.
- 형태 허용 점수는 원출력을 본 뒤 만든 민감도 분석입니다. 엄격 점수를 함께 공개해 해석 범위를 드러냈습니다.
- Ollama Cloud는 직접 API, Claude와 Codex는 각 CLI를 사용했으므로 제공자 하네스가 완전히 같지는 않습니다.

## 재현과 원자료

- 과제와 기대값: [`tasks.json`](tasks.json)
- 출력 계약: [`output-schema.json`](output-schema.json)
- Claude·Codex 원출력: [`cli-results/`](cli-results/)
- Ollama Cloud 원출력: [`ollama-results/`](ollama-results/)
- 엄격 점수: [`scores-exact.json`](scores-exact.json)
- 형태 허용 점수: [`scores-patterns.json`](scores-patterns.json)

```powershell
& .\scripts\run_naturalness_effect_cli.ps1 `
  -OutputRoot evals\naturalness-effect-v4\cli-results `
  -Concurrency 2 `
  -SkipFinished

& .\scripts\run_naturalness_effect_ollama.ps1 `
  -OutputRoot evals\naturalness-effect-v4\ollama-results `
  -Concurrency 1 `
  -RetryCount 2 `
  -SkipFinished

python scripts\score_naturalness_effect.py `
  --tasks evals\naturalness-effect-v4\tasks.json `
  --results evals\naturalness-effect-v4\cli-results evals\naturalness-effect-v4\ollama-results `
  --coverage-mode exact `
  --output evals\naturalness-effect-v4\scores-exact.json

python scripts\score_naturalness_effect.py `
  --tasks evals\naturalness-effect-v4\tasks.json `
  --results evals\naturalness-effect-v4\cli-results evals\naturalness-effect-v4\ollama-results `
  --coverage-mode patterns `
  --output evals\naturalness-effect-v4\scores-patterns.json
```

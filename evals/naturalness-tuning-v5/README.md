# 한 줄을 더 강조하면 수정문이 실제로 충실해지는가

## 결론부터 말하면: 이번 후보는 채택하지 않는다

v4에서 현재 스킬은 이상한 표현을 잘 제거했지만, 수정문을 짧게 만들면서 대상·동작·조건·범위를 다시 생략하는 문제가 남았습니다. 그래서 다음 한 문장을 후보 스킬에 추가했습니다.

> 수정문을 짧게 만드는 것보다, 문제 표현이 대신하던 대상·동작·조건·범위를 문맥에서 확인해 수정문 안에 빠짐없이 되돌려 놓는다.

새 합성 표본에서 10개 모델을 세 번씩 비교한 결과, 후보의 핵심 의미 포함률은 10.6%에서 11.7%로 1.1%p, 수정 성공률은 10.0%에서 10.8%로 0.8%p 높아지는 데 그쳤습니다. 사전에 정한 채택 기준은 각각 +10%p와 +8%p였습니다. 후보는 이 두 기준을 통과하지 못했으므로 배포 스킬에 반영하지 않습니다.

## 왜 새 실험이 필요했는가

v4에서는 다음과 같은 실패가 있었습니다.

> 500대 fleet의 route recalculation fan-out을 제어한다.
>
> → 로봇 경로 재계산 작업의 동시 처리 묶음 수를 제한한다.

영어식 결합은 사라졌지만 500대, 25대씩, 최대 네 묶음이라는 범위도 함께 사라졌습니다. 문제 표현을 제거하는 것과 그 표현이 가리키던 사실을 되살리는 것은 서로 다른 과제였습니다.

이번에는 v4 결과를 보지 않은 새 사례 15개를 만들고, 결과 생성 전에 다음 항목을 [`protocol.md`](protocol.md)에 적어 커밋 `6fdd0e3`으로 공개했습니다.

- 후보 지침의 정확한 문구
- 합성 사례와 허용 정규식
- 10개 모델과 세 번의 반복
- 현행/후보 비교 방식
- 여섯 개 채택 기준

결과를 본 뒤 후보나 합격선을 바꾸지 않았습니다.

## 실험 방법

### 표본

[`tasks.json`](tasks.json)에는 회사 문서를 사용하지 않은 합성 사례 15개가 있습니다.

- 이상 표현 12개: 혼합어, 비유, 명사 압축, 설명을 대신하는 평가, 음역어, 구어적 비유 각 2개
- 대조 문장 3개: 코드 식별자, 표준 기술 용어, 이미 명확한 문장

모든 이상 표현에는 뜻을 확정할 수 있는 문맥을 붙였습니다. 모델은 의미를 물어보는 대신 해당 사실로 수정문을 만들 수 있습니다.

### 모델과 호출

2026년 9월 3일 Claude Code 2.0.73, Codex CLI 0.151.0-alpha.7.2와 Ollama Cloud Responses API에서 실행했습니다.

| 경로 | 모델 지정값 |
|---|---|
| Claude Code | `claude-fable-5`, `sonnet`, `claude-haiku-4-5` |
| Codex CLI | `gpt-5.6-sol`, `gpt-5.4-mini`, `gpt-5.3-codex-spark` |
| Ollama Cloud | `kimi-k3`, `glm-5.2`, `qwen3.5:397b`, `gpt-oss:120b` |

각 모델에 현행 스킬과 후보 스킬을 각각 3회 적용했습니다. 총 60회 호출에서 900개 사례 판정을 얻었고, 이상 표현 판정은 720개입니다. 60회 모두 전송과 JSON 생성에 성공했습니다. `sonnet`은 CLI 별칭이므로 고정된 모델 버전으로 취급하지 않습니다.

### 점수

주평가에는 실행 전에 확정한 `required_patterns`를 사용했습니다.

- **이상 표현 제거율:** 미리 정한 문제 표현이 수정문에서 사라졌는가?
- **핵심 의미 포함률:** 수정문에 사전 정의한 대상·동작·조건·범위가 남았는가?
- **수정 성공률:** 기대 판정, 실제 수정, 이상 표현 제거, 핵심 의미 포함, 근거 없는 내용 미추가를 모두 만족했는가?
- **정상 문장 보존율:** 명확한 대조 문장을 통과시키고 수정하지 않았는가?
- **의미 안전률:** 문맥에 없는 금지된 가정을 추가하지 않았는가?

형태를 전혀 허용하지 않는 엄격 문자열 점수도 민감도 분석으로 함께 계산했습니다.

## 결과

### 전체 결과

| 지표 | 현행 스킬 | 후보 스킬 | 차이 | 사전 기준 |
|---|---:|---:|---:|---:|
| 핵심 의미 포함률 | 10.6% | 11.7% | **+1.1%p** | +10%p 이상 |
| 수정 성공률 | 10.0% | 10.8% | **+0.8%p** | +8%p 이상 |
| 이상 표현 제거율 | 85.3% | 86.1% | +0.8%p | -2%p 이상 |
| 정상 문장 보존율 | 100% | 100% | 0%p | 95% 이상, 차이 -2%p 이상 |
| 의미 안전률 | 100% | 100% | 0%p | 99% 이상 |

엄격 문자열 기준에서도 핵심 의미 포함률은 10.6%→11.4%, 수정 성공률은 10.0%→10.6%에 그쳤습니다. 형태 허용 방식만의 우연한 결과는 아니었습니다.

모델 분포 기준은 통과했습니다. 10개 중 8개에서 수정 성공률이 낮아지지 않았고 4개에서 높아졌습니다. 하지만 평균 개선 폭에 관한 두 핵심 기준을 충족하지 못했으므로 최종 판정은 [`adoption-decision.json`](adoption-decision.json)의 `hold`입니다.

### 후보가 도움이 된 사례도 반복되지는 않았다

`gpt-5.6-sol`의 TUNE-01에서는 후보가 세 번 중 한 번 저장 결과까지 되살렸습니다.

| 조건 | 실제 수정문 |
|---|---|
| 현행 | 사용자가 속한 기관의 권한 설정과 공통 역할 설정에 포함된 허용 메뉴를 합친다. |
| 후보 | 사용자가 속한 기관의 권한 설정과 공통 역할 설정에 포함된 허용 메뉴를 합쳐 사용자별 유효 메뉴 권한으로 저장한다. |

그러나 후보의 나머지 두 번은 현행과 마찬가지로 저장 결과를 생략했습니다. 같은 모델의 TUNE-04도 세 번 중 두 번만 후보가 `응답하지 않음`, 값 없는 문항, 합계와 분모, 평균 계산을 모두 남겼습니다. 한 줄 지침이 특정 출력에는 영향을 주었지만 안정적인 절차로 작동하지 않았습니다.

Fable 5의 TUNE-07은 더 직접적인 개선 사례였습니다. 현행 출력은 `approval matrix`와 `effective rule`을 다시 사용했지만, 후보는 세 번 중 두 번 다음처럼 실제 규칙을 풀어 썼습니다.

> 권한 서비스는 직급 기본 규칙, 부서별 추가 규칙, 사용자별 임시 예외를 순서대로 적용해 사용자별 최종 승인 한도를 미리 계산해 저장한다.

그럼에도 Fable 전체 수정 성공률 개선은 13.9%→19.4%에 머물렀습니다.

### 일부 모델에서는 오히려 퇴행했다

Haiku 4.5의 이상 표현 제거율은 86.1%에서 69.4%로 낮아졌습니다. 후보 조건에서 다음과 같이 원래 문제 표현을 다시 남겼습니다.

> 정산 리컨실리에이션 배치가 차이 내역을 예외 목록에 기록한다.
>
> 세 가지 approval matrix 규칙을 계산해 사용자별 effective rule을 미리 저장한다.
>
> 서버 기동 시 캐시를 미리 데워두면 배포 직후 응답 지연이 크게 줄어든다.

Kimi K3의 수정 성공률도 47.2%에서 30.6%로 낮아졌습니다. 일부는 실제 의미 손실이 아니라 `변경 전·후`와 `변경 전`, `변경 후`를 따로 찾는 사전 정규식의 엄격함 때문입니다. 그러나 그런 명백한 형태 차이를 수동으로 인정해도 전체 후보가 요구한 +8%p 개선에 도달할 만큼 사례 수가 많지 않습니다. 따라서 채택 판정은 달라지지 않습니다.

## 왜 한 문장이 효과가 없었는가

후보 문장은 새 절차라기보다 현행 스킬의 기존 지시를 다시 말했습니다. 현행 스킬에는 이미 다음 내용이 있습니다.

- 수정 뒤 actor, direction, condition, scope와 code-level meaning을 보존했는지 판정한다.
- 실제 동작이 드러난다면 조금 긴 문장이 대체로 낫다.

여기에 “빠짐없이 되돌려 놓는다”를 더해도 모델이 무엇을 추출하고 어떻게 대조해야 하는지는 달라지지 않았습니다. 강한 모델에서는 가끔 누락을 줄였지만, 다른 모델에서는 중복 지침이 행동을 안정시키지 못했고 일부 경량 모델에는 부담이 됐습니다.

다음 후보는 결과를 한 번 더 요구하는 문장이 아니라 다음과 같은 **검사 절차**여야 합니다.

> 수정하기 전에 문제 표현이 가리고 있는 사실을 대상·동작·조건·범위로 나누어 적고, 수정 뒤 각 항목이 남았는지 대조한다.

이 문구는 이번에 시험하지 않았으므로 배포 스킬에 넣지 않습니다. 또한 다음 평가에서는 문맥의 모든 세부사항이 아니라, 검토 대상 문장이 실제로 대신하고 있던 최소 의미 단위를 실행 전에 구분해야 합니다.

## Ollama Cloud 상태

Ollama Cloud 24회는 동시성 1, 429에 한한 최대 2회 재시도 조건으로 모두 완료됐습니다. 429는 발생하지 않았습니다. 입력 113,967토큰, 출력 110,703토큰으로 합계 224,670토큰을 사용했습니다. 이 결과는 실행 시점의 가용성만 보여 주며 장기적인 제한 상태를 보장하지 않습니다.

## 한계

- 모델·조건별 3회이므로 한 번의 우연은 줄였지만 실제 문서 분포를 대표하지 않습니다.
- 핵심 의미 패턴은 실행 전에 고정했지만 일부 자연스러운 축약과 표기 차이를 실패로 셉니다.
- 반대로 금지 가정 검사는 미리 정한 패턴만 찾으므로 모든 의미 변형을 검출하지 않습니다.
- 하나의 긴 요청에 15개 사례를 묶었으므로 개별 요청과 다른 주의력 효과가 있을 수 있습니다.
- 후보 효과와 모델·CLI·제공자 하네스의 상호작용을 완전히 분리하지 못합니다.

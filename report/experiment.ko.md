# AI가 쓴 한국어 기술 문서는 왜 다시 해석해야 할까

## 먼저, 이 문장들을 읽어 보십시오

> 두 variant의 parity를 확보한다.

> 상태를 화면으로 꺼낼 구멍을 연다.

> 월말 마감 후 역분개 수동 검토 분기.

> 분석 단위는 ITT로 두고 FDR을 적용한다.

모두 기술 문서에서 나올 법하고 문법적으로 완전히 틀렸다고 하기도 어렵습니다. 하지만 처음 읽는 사람은 곧바로 구현으로 넘어갈 수 없습니다.

첫 문장에서는 무엇의 수를 같게 한다는 뜻인지, 둘째 문장에서는 구멍이 API인지 속성인지, 셋째 문장에서는 누가 어떤 조건으로 검토하는지 추측해야 합니다. 마지막 문장은 약어를 이미 아는 통계 실무자에게는 짧지만, “처음 읽는 개발자도 구현할 수 있게 설명하라”는 요청에는 충분하지 않습니다.

이때 독자는 대략 다음 일을 합니다.

1. 낱말과 약어를 알아봅니다.
2. 평소 함께 쓰지 않는 결합이나 비유에서 멈춥니다.
3. 앞뒤 문맥과 자신의 도메인 지식으로 빠진 대상과 동작을 추측합니다.
4. 문장을 구체적인 시스템 동작으로 다시 만들어 이해합니다.

문장에 있어야 할 설명을 독자가 대신 조립하는 셈입니다. 이 프로젝트는 이 부담을 “틀린 한국어”나 “번역투”라는 인상만으로 다루지 않고, **대상·주체·동작·조건·결과 중 무엇을 독자가 보충해야 하는가**로 검사합니다.

## 문제는 낯선 단어 하나가 아니다

### 낯선 말의 결합

`variant`, `parity` 같은 용어는 각각 쓰일 수 있습니다. 문제는 `두 variant의 parity`가 어떤 속성을 비교하는지 말해 주지 않는다는 점입니다.

- Before: `두 variant의 parity를 확보한다.`
- After: `두 화면 변형에서 표시되는 필드 수를 같게 맞춘다.`

영어를 모두 한국어로 바꾸는 것이 목표가 아닙니다. 코드 이름, 제품명, 팀에서 합의한 기술 용어는 유지하되 문장 안에 비교 대상과 동작을 넣는 것이 목표입니다.

### 동작을 대신하는 비유

- Before: `상태를 화면으로 꺼낼 구멍을 연다.`
- After: `화면이 상태를 읽을 수 있도록 status 속성을 공개한다.`

비유 자체가 나쁜 것은 아닙니다. 실제 동작이 함께 적혀 있다면 이해를 도울 수도 있습니다. 그러나 비유가 API, 데이터 방향, 실패 결과를 대신하면 독자가 구현을 추측하게 됩니다.

### 명사로 지나치게 압축

- Before: `호출 경유, 변경 불요.`
- After: `이 모듈은 호출 경로에 포함되지만 이번 작업에서는 변경하지 않는다.`

표와 소제목은 짧아야 하지만, 주체와 서술어를 모두 없애도 된다는 뜻은 아닙니다. 특히 누가 무엇을 하지 않는지가 결정 사항이라면 문장으로 남겨야 합니다.

### 평가가 사실보다 앞섬

- Before: `클라이언트만 먼저 배포해도 무해하다.`
- After: `[확인 필요] 구버전 서버가 새 필드를 무시한다면 클라이언트를 먼저 배포해도 기존 기능에는 영향이 없다.`

`무해하다`는 결론만으로는 영향 범위와 전제를 알 수 없습니다. 이 사례는 원문만으로 조건을 확정할 수 없으므로 자연스러운 문장을 지어내는 대신 확인 질문을 남겨야 합니다.

## 실험을 어떻게 공개 가능한 형태로 바꿨나

처음에는 비공개 프로젝트의 Markdown·HTML 200개를 탐색해 표현 후보 40개를 분류했습니다. 이 과정은 문제를 발견하는 데는 유용했지만, 원문과 경로를 공개하면 조직과 시스템을 추측할 수 있습니다. 일부 문장만 익명화해도 코드 이름과 업무 맥락이 남습니다.

따라서 공개 실험에서는 두 종류의 자료를 새로 만들었습니다.

1. 저자가 직접 만든 합성 회귀 사례 20개: 문제 문장 16개와 정상·반례 4개
2. 모델에 사내 정보와 실험 목적을 주지 않고 복잡한 설계 안건을 작성시킨 블랙박스 출력

공개 평가의 근거는 이 자료로 한정합니다. 초기 비공개 탐색은 동기와 하네스 설계에만 사용했고 저장소에는 원문, 프로젝트명, 사람, 경로를 넣지 않았습니다.

## 블랙박스 과제

모델에는 문체를 평가할 것이라는 사실을 알리지 않았습니다. 다음 세 난제를 각각 600자 안팎으로 설명하게 했습니다.

1. **종합정보시스템 권한:** 한 사용자의 여러 신분, 화면·버튼·필드 권한, 휴직, 대리 결재, 임시 권한, 허용·거부 충돌
2. **회계 의사결정:** 선수금, 사용량 요금, 환불, 변동 대가, 본인·대리인, 다중 통화, 마감 뒤 수정
3. **통계 의사결정:** 층화 배정, 결측, 순차 모니터링, 다중 비교, 오염된 대조군, 인과 가정, 중단 기준

문체 실험이라는 전제는 프롬프트에 넣지 않았고, “처음 읽는 개발자도 구현할 수 있게 설명하라”고만 요청했습니다. Claude Code 2.0.73의 Sonnet 별칭과 Codex CLI 0.151.0-alpha.7.2의 gpt-5.4를 사용했습니다. 도구는 사용하지 않았고 Codex는 읽기 전용, 세션 비보존으로 실행했습니다.

Gemini CLI 0.28.0과 `gemini-2.5-pro`도 실행했지만 연결된 계정이 제품 라이선스 오류 403을 반환했습니다. 재로그인이나 API 과금 활성화는 하지 않았습니다. 따라서 Gemini 결과는 비어 있으며 비교에 포함하지 않습니다.

## 결과: 노골적인 비유보다 다른 문제가 더 잘 보였다

이번 여섯 출력에서는 `손잡이`, `뼈대`, `그릇`처럼 눈에 띄는 임의 비유가 거의 나타나지 않았습니다. 이 사실은 중요합니다. 특정 모델이 언제나 같은 이상한 말투를 쓴다는 결론을 뒷받침하지 않기 때문입니다.

대신 세 가지 문제가 반복됐습니다.

### 1. 어려운 용어를 풀라는 요구를 부분적으로만 따름

Claude의 통계 문서는 다음처럼 썼습니다.

> 무작위 배정·SUTVA·단조성 가정이 충족되는지 진단 플롯과 통계 검정으로 확인한다.

Codex의 통계 문서도 다음처럼 썼습니다.

> 분석 단위는 기본적으로 배정 기준을 따르는 ITT로 두고 … 가설군별로 FDR 또는 계층적 보정을 적용한다.

두 문장 모두 통계 실무자에게는 익숙할 수 있지만, 처음 읽는 개발자에게 설명하라는 요구에는 부족합니다. `SUTVA`, `ITT`, `FDR`을 없앨 필요는 없습니다. 처음 등장할 때 뜻과 시스템에서의 역할을 풀어 써야 합니다.

- 개선안: `대상은 실제 참여 여부와 관계없이 최초 배정 집단을 기준으로 분석한다(ITT). 여러 가설을 검정할 때는 거짓 발견 비율(FDR)을 통제한다.`

### 2. 자연스럽지만 사실을 새로 정함

Claude의 회계 문서는 다음 규칙을 제시했습니다.

> 월초 5일까지는 소급 허용, 이후는 당월 조정 분개로 처리한다.

> 일 매출 ₩100만 이하 거래는 … 자동 생성하고, 초과 건은 … 수동 검토한다.

문장은 자연스럽지만 프롬프트에 5일이나 100만 원이라는 기준은 없었습니다. 모델이 가정을 표시하지 않고 정책을 확정했습니다. 문체 검사만으로는 잡기 어려운 **의미·근거 문제**입니다.

### 3. 매끄러운 문장 안의 모순과 모호함

Codex의 권한 문서는 다음 우선순위를 제안했습니다.

> 사용자 직접 거부, 사용자 직접 허용, 역할 거부, 역할 허용 순으로 적용해 거부를 우선한다.

목록대로라면 사용자 직접 허용이 역할 거부보다 먼저인데, 뒤에서는 거부가 우선한다고 말합니다. “거부 우선”이 모든 계층에 적용되는지, 직접 부여가 역할보다 우선하는지 확정해야 합니다.

Claude의 회계 문서에는 다음 표현이 있습니다.

> 이미 인식한 수익을 `revenue_recognition`에서 음수로 차감한다.

음수를 차감하면 수익이 늘어난다고 읽을 수도 있습니다. `같은 금액의 차감 전표를 생성한다`처럼 방향을 한 가지로 표현하는 편이 안전합니다.

## 무엇이 더 자연스러웠나를 세지 않은 이유

문서가 자연스러운지는 중요하지만 하나의 점수로 합치면 위험합니다. 문장이 매끄러워지면서 주체나 회계 정책이 바뀔 수 있기 때문입니다. 이 프로젝트는 적어도 다음 두 축을 분리합니다.

| 축 | 질문 | 실패 예시 |
|---|---|---|
| 독해 명료성 | 독자가 대상과 동작을 문장 안에서 알 수 있는가? | 약어와 명사 나열만 남음 |
| 의미 보존 | 주체, 방향, 조건, 범위, 확실성이 유지됐는가? | 없던 금액·기간·정책을 추가함 |

현재 표본은 모델별 3건, 각 1회뿐입니다. 따라서 모델 우열이나 세대별 경향을 말할 수 없습니다. 이 결과가 보여 주는 것은 “자연스러운 한국어” 한 줄만으로는 문체와 사실 보존을 동시에 보장하기 어렵다는 점입니다.

## 제안: 작성, 검사, 교정, 검증을 분리한다

### 1. 작성 또는 재작성

```text
제공된 사실과 코드 식별자를 사용해 대상과 실제 동작을 직접 쓴다.
필요한 주체, 조건, 결과를 문장 안에 밝힌다.
확정할 수 없는 정책이나 수치는 [확인 필요]로 남긴다.
제목, 표, 목록, 캡션에도 같은 기준을 적용한다.
```

이 단계에는 긴 금지어 목록을 넣지 않습니다. 특정 단어를 다시 생성하게 만드는 부정 프라이밍과 정상 용어의 과잉 교정을 줄이기 위해서입니다.

### 2. 생성 결과 검사

검사기는 문장을 바로 고치지 않고 다음을 보고합니다.

- 독자가 추측해야 하는 정보
- 빠지거나 모호한 대상·주체·동작·조건·결과
- `구체화 필요` 또는 `의미 확인 필요`
- 가능한 수정안과 확인할 사실

### 3. 제한 교정

검사에서 표시된 문장만 수정합니다. 원문만으로 확정되지 않는 뜻은 자연스럽게 지어내지 않고 질문으로 남깁니다.

### 4. 의미 검증

수정 전후의 주체, 입출력 방향, 조건, 결과, 범위, 확실성, 코드 식별자를 따로 비교합니다. 문체가 좋아져도 이 중 하나가 달라졌다면 실패입니다.

## 설치형 하네스

이 절차는 `korean-technical-writing-review` Agent Skill로 만들었습니다.

```bash
npx skills add JooyoungChoi14/korean-technical-writing-for-llms --skill korean-technical-writing-review
```

스킬은 특정 모델명을 기준으로 문서를 판별하지 않습니다. Markdown, HTML 설명, 설계서, 계획서, ADR, README, 커밋 메시지, UI 문구를 같은 원칙으로 검사합니다. 영어 단어나 비유가 있다는 이유만으로 지적하지 않고, 그 표현 때문에 필요한 정보가 빠졌을 때만 표시합니다.

## 결론

좋은 한국어 기술 문서는 “한국어처럼 들리는가”에서 끝나지 않습니다. 독자가 구현과 판단에 필요한 대상과 동작을 문장 안에서 얻을 수 있어야 하며, 자연스럽게 고치는 동안 새로운 사실이 생기지 않아야 합니다.

이번 소규모 블랙박스 실험에서는 두 모델 모두 대체로 읽을 만한 문장을 만들었지만, 어려운 용어를 설명하지 않거나, 근거 없는 정책을 확정하거나, 매끄러운 문장 안에 모순을 남기는 사례가 나타났습니다. 해결책은 모델별 금지어 사전보다 **독자의 추론 부담을 찾는 검사와 의미 보존 검증을 생성 단계와 분리하는 것**에 가깝습니다.

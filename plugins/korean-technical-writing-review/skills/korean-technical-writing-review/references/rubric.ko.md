# 한국어 기술 문서 검토 기준

## 판정 단위

단어가 아니라 문장이 제공하는 정보로 판정한다. 같은 단어도 대상과 동작이 분명하면 허용할 수 있다.

### 1. 낯선 결합

영어 일반어·임의의 음역어·약칭을 한국어 조사나 한자어와 결합해, 원래 개념을 아는 사람만 뜻을 복원할 수 있는가?

- 문제 후보: `두 variant의 parity 확보`
- 확인할 정보: 무엇의 어떤 속성을 같게 하는가?
- 가능한 수정: `두 변형에서 표시되는 항목 수를 같게 맞춘다.`

코드의 타입명, 함수명, 제품명, 팀 용어집에 있는 말은 영어라는 이유만으로 지적하지 않는다.

### 2. 동작을 대신하는 비유

입력·저장·호출·반환·검증·노출 같은 동작을 손잡이, 관문, 뼈대, 껍데기 같은 사물이나 이동으로만 설명하는가?

- 문제 후보: `상태를 화면으로 꺼낼 구멍을 연다.`
- 확인할 정보: 어느 속성 또는 API를 추가하며 값은 어느 방향으로 흐르는가?
- 가능한 수정: `화면이 상태를 읽을 수 있도록 status 속성을 공개한다.`

비유 뒤에 실제 동작이 함께 설명되어 있다면 무조건 지적하지 않는다.

### 3. 명사 나열과 과도한 압축

주체와 서술어가 빠져 독자가 조사와 동작을 채워야 하는가?

- 문제 후보: `호출 경유, 변경 불요`
- 가능한 수정: `이 모듈은 호출 경로에 포함되지만 이번 작업에서는 변경하지 않는다.`

표 제목처럼 공간이 제한된 경우에도 뜻을 잃지 않는 최소한의 서술어를 권한다.

### 4. 평가가 사실을 대신함

안전, 무해, 자멸, 오염, 무의미 같은 판단이 영향 범위와 조건보다 먼저 나오거나 그 설명을 대신하는가?

- 문제 후보: `클라이언트 변경만으로는 무의미하다.`
- 확인할 정보: 무엇이 구현되지 않으면 어떤 기능이 동작하지 않는가?
- 가능한 수정: `서버가 식별자를 보내지 않으면 클라이언트만 변경해도 개별 취소 기능은 동작하지 않는다.`

### 5. 정보 순서

독자가 결론을 이해하기 전에 전제나 용어 정의를 뒤에서 찾아야 하는가? 필요한 배경 → 대상 → 동작 → 조건/결과의 순서로 읽히는지 확인한다.

### 6. 전 영역 검사

본문뿐 아니라 제목, 소제목, 표, 목록, 캡션, 버튼·상태 문구도 같은 기준으로 확인한다. 짧은 텍스트는 모델이 놓치기 쉽다.

## 판정값

- `통과`: 문장 자체로 필요한 정보가 충분하다.
- `구체화 필요`: 뜻은 확정할 수 있으나 대상·동작·조건·결과 일부가 표현에 가려졌다.
- `의미 확인 필요`: 자연스럽게 고칠 수는 있지만 원문만으로 정확한 뜻을 확정할 수 없다.
- `검사 제외`: 코드, 인용문, 외부 제품명, 증거로 보존해야 하는 원문이다.
